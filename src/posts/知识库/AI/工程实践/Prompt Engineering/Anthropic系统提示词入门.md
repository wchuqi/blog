这是 Anthropic 官方 Prompting 101 系列的一节，两位主讲（Hannah、Christian）来自 Applied AI 团队。全程不需要你懂提示词术语，因为它就是**在一个真实场景里一步步把 prompt 搭起来**，每加一块就现场跑一次，看输出怎么变。这种「加一块、跑一次、看差异」的演示比罗列技巧有用得多。

> 视频来源：[Anthropic：系统提示词入门](https://www.bilibili.com/video/BV1BshVzaEEC/)（B 站搬运，UP 主 i陆三金，英文原声约 24 分钟）。本文按 ASR 转写整理，不是逐句翻译；转写错处见文末「转写可疑之处」。

## 场景

瑞典的一家车险公司，每天处理交通事故理赔。每次给模型两样东西：

- **一张事故报告表单**：瑞典语，17 行复选框，左右两列分别代表车辆 A 和车辆 B，记录事故发生前两车各自做了什么。
- **一张手绘事故草图**：当事人自己画的，画的就是这次事故。

要模型回答的问题只有两个：表单上勾了什么、责任在谁。

这个场景选得很好，因为它把「模型要看的是一张图」这个难点和「业务规则藏在表单结构里」这个难点叠在了一起——表单本身永远不变，变的是每一行被勾成什么样。

## 第一次尝试的失败：它说是滑雪事故

把两张图 + 一句「审核事故报告表单，判断发生了什么、谁的责任」丢进 Console（temperature 0，max_tokens 拉满，用的是 Claude 4 系列模型），结果模型说这是**一起发生在某条瑞典街道上的滑雪事故**。

错得很典型，而且原因也好理解：prompt 里**没有任何东西设定场景**。模型只知道要给一个「事故报告」下判断，于是从图里抓了它见过的、最像事故报告的东西。主讲人从这里引出全篇的立场：

> Prompt engineering 是一门**迭代的、经验的**学问。你几乎可以把每次失败直接变成一个测试用例——「模型必须知道这是车祸，与滑雪无关」——然后针对性地往 prompt 里补。

## 官方推荐的 Prompt 结构（十个组件）

幻灯片给出的结构是下面十项，视频逐个走了一遍：

| # | 组件 | 作用 | 视频里在哪 |
|---|---|---|---|
| 1 | Task context 任务上下文 | 你是谁、在什么场景里工作 | v2 |
| 2 | Tone context 语气上下文 | 要什么口吻、什么严格程度 | v2 |
| 3 | Background data / documents / images 背景资料 | 每次都一样的静态知识 | v3 |
| 4 | Detailed task description & rules 详细任务描述与规则 | 分步骤怎么做 | v4 |
| 5 | Examples 示例 | few-shot，含图示例 | 幻灯片 |
| 6 | Conversation history 会话历史 | 多轮上下文 | 幻灯片 |
| 7 | Immediate task description / request 当下请求 | 把要它立刻做的事再重申一次 | v5 |
| 8 | Output formatting 输出格式 | 便于下游解析 | v5 |
| 9 | Prefilled response 预填回答 | 强制输出开头，砍掉前言 | 幻灯片 |
| 10 | Thinking step by step 分步思考 | 让它显式推理 | 幻灯片（extended thinking） |

有一条贯穿始终的判断值得先记住：**第 3 项（不变的背景）放 system prompt，本次的素材（两张图）放 user message**。理由是 system prompt 里的静态内容可以吃到 prompt caching，而且模型不用每次重新猜「这张表是什么」。

## 迭代过程

### v2：补任务上下文和语气

加了两样东西：

- **任务上下文**：这个 AI 系统是在帮一位人类理赔员审核瑞典语的车祸报告表单，模型同时还会收到一张当事人手绘的现场草图。
- **语气上下文**：保持事实性和确定性；**如果没有完全把握，就不要下结论**，不要猜。

同时把数据讲清楚给观众听：表单是 17 行、两列（车 A / 车 B），草图是同一件事的另一份数据。

结果：模型**不再说是滑雪**了，正确读出车 A 勾在第 1 行、车 B 勾在第 12 行。但它最后说信息不足，无法判定责任。

这正是想要的行为——「不要猜」的约束生效了。同时也暴露出下一步该补什么：它对这张表单本身了解得太少。

### v3：把表单的静态知识放进 System Prompt

这一版往 system prompt 里写进了关于表单的一切：

- 这是一张瑞典语车祸表单，有标题、有两列，两列分别代表哪辆车；
- **17 行每一行分别是什么含义**；
- **这张表是怎么被填的**——人类手填，所以不会规整：可能画圈、可能涂改、可能没打 ×，读的时候要能认出各种标记；
- 这张表在业务里的用途和解读方式。

效果有两层。一层是可观测的：模型花更少篇幅跟我们复述「这张表是什么」，直接把读到的勾选项列出来。另一层是结论变了：它现在敢说**车 B 有责任**，理由来自表单 + 草图。

顺带一个提示：这些每次都一样的表单说明，是 prompt caching 最典型的适用对象。

### v4：写清分析的先后顺序

这一版在 system prompt 里加了详细的分步指令，关键是**顺序**：

1. 先仔细看表单，确认哪些框被勾了，一个都别漏，先把它们列出来；
2. 确信自己从表单里拿到的信息之后，再去看草图；
3. 读草图时，时刻带着「目前为止你了解到的事故经过」——把草图跟表单对上，最后再下判定。

为什么顺序重要：**人类也是这么做的**。先看草图只会看到一堆框和线，根本不知道在画什么；先看表单知道是车祸、知道两车各做了什么，草图才有意义。

结果：模型开始「展示过程」，逐框报告勾没勾（主讲人点评说这有点啰嗦，可能不是最终想要的），并且按 XML 标签分段输出——表单分析、事故摘要、草图分析——结论仍然是车 B 有责任。

### v5：重申当下任务 + 固定输出格式

最后一版加了 guidelines / reminder 段落，说白就是把要求再钉一遍：

- 摘要要清晰、简洁、准确；
- 不要有任何东西妨碍判断本身的准确性（该忽略的噪声就忽略）；
- **把最终判定包在一个专用 XML 标签里**（视频里叫 "final verdict"）。

最后一条是给**下游程序**准备的：数据工程师不关心前面那段漂亮的分析文字，只想要能存进数据库的那一小段。有了固定标签，前面的推理照常输出、后面用正则或 XML 解析器取判定就行。

结果：输出明显更紧凑，判定被包在标签里，可以直接解析。整个 demo 的轨迹也串起来了——从「滑雪事故」，到「车祸但不敢下结论」，到「格式严格、可直接对接应用」。

## 幻灯片补的几个组件

**示例（few-shot）**是引导模型最有力的手段之一，而且**示例可以是图**：把图片 base64 编码后放进示例里，再配上「这种情况下应该怎么解读」的说明。真正落地时，一家保险公司会积累几十上百个「灰色地带」的案例——那些人类靠直觉才能判对、模型容易判错的事故——把它们固化进 system prompt，下次遇到类似的就有参照。

**会话历史**属于同一思路：把与当前任务相关的多轮上下文（真实的对话、或上游系统生成的历史）放进 system prompt。这个 demo 不是面向用户的，所以没用上；如果是一个陪用户长谈的应用，这块就很关键。

**预填回答（prefilled response）**是另一条控制输出的路子：直接规定它必须以什么开头。想要 JSON 就让它以 `{` 开头，想要按标签切分就让它以那个标签开头。好处是不需要额外要求它「不要写前言」，它根本没有机会写前言。

**扩展思考（extended thinking）**在 Claude 3.7 和 Claude 4 上都可用。视频提醒了一个很实用的用法：**把 extended thinking 当成写 prompt 的拐杖**。打开它，模型会把推理过程写在 thinking 块里，你可以读这份「草稿」看它是怎么处理你给的数据的；然后照着它的推理路径，把顺序和要点固化进 system prompt。这比每次请求都开 thinking 更省 token，而且能让你真正理解「一个没有人类直觉的模型是怎么读你的数据的」。

## 可以照搬的清单

1. 先写失败版本。列出每个失败对应的测试用例，再决定往 prompt 里加什么。
2. 不变的知识进 system prompt（吃到缓存），本次素材进 user message。
3. 显式规定**分析顺序**，尤其是当素材有先后依赖时（先读结构化的，再读非结构化的）。
4. 明确说「不确定就说不确定、不要猜」，并考虑要求它在做事实断言时给出依据（「因为第 2 行明确被勾选」）。
5. 用 XML 标签把「输入素材」和「输出段落」都切开，模型对这种结构反应很好。
6. 让输出以固定标签或 `{` 开头，下游直接解析，顺带砍掉前言。
7. 拿 extended thinking 的 thinking 块当调试工具，而不是当成长期方案。
8. 静态的大段背景知识，先确认是否适合 prompt caching，再决定放哪。

## 转写可疑之处

ASR 把不少专有词听错了，下面按上下文推断，不是视频原话：

- `cloud` / `claw` / `call` / `god` → 都是 **Claude**。
- `apply day i team` → **Applied AI team**。
- 那条被模型编出来的瑞典街道名（转写成 `chapangartan`）几乎肯定是误识别，别当真。
- `base sixty four encoday` → **base64 encoding**。
- `important skylines` → **important guidelines**；`imparse` → and parse；`prefil` → prefilled。
- 模型名转写成 `the new four solid model` / `call four`，最可能是 **Claude 4 Sonnet**，但不确定，文中只写「Claude 4 系列」。
- `car action report form` → car accident report form。
