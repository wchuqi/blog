# 向量数据库原理
> 向量数据库的"心脏"是 ANN 索引算法和距离度量——理解它们，你就能在任何向量存储方案上做出正确决策。
**Category**: AI 基础设施 / 算法与架构
**Difficulty**: Intermediate
**Prerequisites**: 基本的线性代数概念（向量、距离、内积）、了解 Embedding 模型的基本原理

## 什么是向量数据库？

### 定义

**向量数据库（Vector Database）** 是一种专门用于存储、索引和查询高维向量（embedding）的数据库系统。与传统数据库通过精确匹配（`WHERE id = 42`）检索数据不同，向量数据库通过**相似性搜索**（similarity search）找到与查询向量最"接近"的数据。

### 一个直觉类比

想象你走进一个巨大的图书馆，想找一本"关于一个孤独老人在海上与大鱼搏斗"的书。传统数据库就像按 ISBN 或书名查找——你必须知道确切的编号。而向量数据库就像一位博学的图书管理员，他理解你描述的**语义**，能直接带你走到《老人与海》旁边，甚至还能推荐《白鲸》和《蓝色海豚岛》。

### 为什么需要向量数据库？

现代 AI 模型（如大语言模型、图像识别模型）将非结构化数据——文本、图片、音频、视频——转换为**高维向量**（embedding）。这些向量是理解数据"含义"的数学表示。但问题来了：

- 一个 1536 维的向量占 6KB（float32），1 亿个向量就是 600GB
- 在高维空间中做精确最近邻搜索（Exact KNN）的时间复杂度是 O(n·d)，对于大规模数据集完全不可行
- 传统 B-tree 索引在高维空间中退化为全表扫描（**维度灾难**）

向量数据库通过**近似最近邻搜索（ANN）** 算法，在可接受的精度损失下将搜索速度提升几个数量级。

### 发展简史

| 时期 | 里程碑 |
|------|--------|
| 1970s | K-D Tree 等空间索引结构被提出 |
| 1990s | 局部敏感哈希（LSH）理论发展 |
| 2010s | FAISS（Facebook）发布，大规模向量搜索成为可能 |
| 2016 | Annoy（Spotify）开源 |
| 2017 | HNSW 论文发表，成为主流索引算法 |
| 2019-2021 | Pinecone、Milvus、Weaviate、Qdrant 等专业向量数据库涌现 |
| 2023-2025 | RAG 爆发，向量数据库成为 AI 基础设施核心组件；传统数据库（PostgreSQL、Elasticsearch）纷纷集成向量搜索能力 |


## 核心概念

### 1. 向量（Vector / Embedding）

向量是向量数据库的基本数据单元。它是一个固定长度的浮点数数组，表示数据在某个语义空间中的位置。

```python
# 一个 768 维的文本向量示例（通常由 embedding 模型生成）
text_vector = [0.023, -0.156, 0.892, ..., 0.041]  # 768 个浮点数
```

不同的 embedding 模型产生不同维度的向量：

| 模型 | 维度 | 适用场景 |
|------|------|----------|
| `text-embedding-3-small`（OpenAI） | 1536 | 通用文本 |
| `text-embedding-3-large`（OpenAI） | 3072 | 高精度文本 |
| `bge-large-zh`（BAAI） | 1024 | 中文文本 |
| `CLIP ViT-L/14` | 768 | 图文多模态 |
| `all-MiniLM-L6-v2` | 384 | 轻量级文本 |

### 2. 相似度度量（Similarity Metric）

向量之间的"距离"决定了搜索结果的质量。常用度量方式：

#### 余弦相似度（Cosine Similarity）

衡量两个向量的**方向**是否一致，忽略大小。值域 [-1, 1]，1 表示完全相同方向。

```
similarity(A, B) = (A · B) / (||A|| × ||B||)
```

> 💡 **适用场景**：文本语义搜索。大多数 embedding 模型已经将向量归一化，此时余弦相似度等价于内积。

#### 欧氏距离（L2 Distance）

衡量两个向量在空间中的**绝对距离**。值越小越相似。

```
distance(A, B) = √Σ(Ai - Bi)²
```

> 💡 **适用场景**：图像特征匹配、需要考虑向量"大小"的场景。

#### 内积（Inner Product / Dot Product）

```
score(A, B) = Σ(Ai × Bi)
```

> 💡 **适用场景**：向量已归一化时，等价于余弦相似度且计算更快。推荐度最高的度量方式。

```python
import numpy as np

def cosine_similarity(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

def l2_distance(a, b):
    return np.sqrt(np.sum((a - b) ** 2))

def dot_product(a, b):
    return np.dot(a, b)

# 示例
a = np.array([0.1, 0.3, 0.5])
b = np.array([0.2, 0.4, 0.4])

print(f"余弦相似度: {cosine_similarity(a, b):.4f}")  # 0.9926
print(f"欧氏距离:   {l2_distance(a, b):.4f}")        # 0.1732
print(f"内积:       {dot_product(a, b):.4f}")         # 0.3400
```

> ⚠️ **重要**：选择错误的相似度度量会导致搜索结果完全不可用。

通用规则：
- 如果 embedding 模型输出的向量已经**归一化**（模为 1），使用**内积**（等价于余弦相似度，但更快）
- 如果向量未归一化且你关心语义方向，使用**余弦相似度**
- 如果你关心绝对差异（如图像像素特征），使用**欧氏距离**

### 3. 近似最近邻搜索（ANN）

精确的 K 近邻搜索需要遍历所有向量，时间复杂度 O(n·d)。ANN 算法用**可接受的精度损失**换取**数量级的速度提升**。

核心思想：不搜索整个空间，而是利用数据结构跳过大部分不可能是结果的向量。

```
┌─────────────────────────────────────────────────────┐
│              精确 KNN vs ANN                         │
│                                                     │
│  精确 KNN:  遍历 100 万个向量 → 100% 准确, 500ms    │
│  ANN:       搜索 ~5000 个向量 → 95% 准确, 5ms       │
│                                                     │
│  对于大多数应用, 95% 的召回率已经足够好               │
└─────────────────────────────────────────────────────┘
```

衡量 ANN 算法的核心指标：

| 指标 | 含义 |
|------|------|
| **Recall（召回率）** | 找到的真实最近邻占全部最近邻的比例。越高越好 |
| **QPS（每秒查询数）** | 吞吐量 |
| **延迟（Latency）** | 单次查询耗时（P50/P99） |
| **内存占用** | 索引结构占用的内存 |
| **构建时间** | 创建索引所需时间 |


## 索引算法详解

索引算法是向量数据库的"心脏"。不同算法在速度、精度、内存之间做出不同权衡。

### HNSW（Hierarchical Navigable Small World）

**当前最主流的索引算法**，基于图结构。

```
Layer 2 (最上层):  ●──────────●          稀疏, 长距离连接
                   │          │          用于快速定位大致区域
Layer 1:        ●──●────●────●──●        中等密度
                   │    │    │
Layer 0 (最底层): ●──●──●──●──●──●──●    最密集, 精细搜索
                   ↑
                 查询入口
```

**工作原理**：

1. **构建阶段**：逐个插入向量，每个向量在多个层级上与最近邻建立连接
2. **搜索阶段**：从最高层开始，贪心地跳到最近邻节点，逐层下降并细化搜索
3. **参数**：
   - `M`：每个节点的最大邻居数（通常 16-64）
   - `ef_construction`：构建时的搜索宽度（越大越精确，构建越慢）
   - `ef_search`：查询时的搜索宽度（越大召回率越高，查询越慢）

**优点**：搜索速度快、召回率高、支持动态增删
**缺点**：内存占用大（需要存储图结构）、构建较慢

> 💡 **直觉理解**：HNSW 就像一个多层地图。顶层是高速公路网（只有大城市之间的连接），底层是城市街道网（所有小路都连通）。你先在高速上快速接近目标区域，再下到街道上精确找到目的地。

### IVF（Inverted File Index）

基于聚类的索引，思想类似倒排索引。

```
向量空间被划分为多个 Voronoi 单元:

    ┌───────┬───────┐
    │ Cell 1│ Cell 2│
    │  ●●●  │  ●●   │    查询时:
    │  ●    │  ●●●  │    1. 找到最近的 nprobe 个聚类中心
    ├───────┼───────┤    2. 只在这些聚类中搜索
    │ Cell 3│ Cell 4│
    │  ●●   │  ●    │
    │  ●●●  │  ●●   │
    └───────┴───────┘
```

**参数**：
- `nlist`：聚类数量（通常 √n，n 为数据量）
- `nprobe`：查询时搜索的聚类数（越大召回率越高，速度越慢）

**优点**：内存占用小、构建快、支持批量添加
**缺点**：召回率不如 HNSW、数据分布不均匀时效果差

> 💡 **直觉理解**：IVF 就像把图书馆的书按主题分到不同房间。找书时先判断目标在哪个房间（聚类），只在那几个房间里仔细翻找，而不是搜遍整栋楼。

### PQ（Product Quantization，乘积量化）

向量压缩技术，常与 IVF 结合使用（IVF-PQ）。

```
原始向量 (128维):
[0.1, 0.3, ..., 0.5, 0.2, ..., 0.8]
        ↓ 分成 8 个子空间, 每个 16 维
    子空间1  子空间2  ...  子空间8
        ↓ 每个子空间用聚类中心 ID 替代
    [  42,     17,   ...,    91  ]   ← 8 个字节代替 512 字节
```

**优点**：内存压缩比极高（可达 32x-64x）
**缺点**：精度有损失、不适合高召回率场景

> 💡 **直觉理解**：PQ 就像用颜色名称（"深蓝"、"浅红"）代替精确的 RGB 数值。虽然损失了一些精度，但存储空间大幅缩小。

### Flat（暴力搜索）

不做任何索引，逐个计算距离。

```python
# 伪代码
def flat_search(query, all_vectors, k):
    distances = [distance(query, v) for v in all_vectors]
    return sorted(distances)[:k]
```

**适用场景**：数据量小（< 10 万）或需要 100% 召回率时。

## 元数据过滤

向量数据库不只存储向量本身，还存储与之关联的**元数据**（metadata）。搜索时可以同时用向量相似度 + 元数据条件进行过滤。

```python
# 示例：搜索相似文档，但只看最近 30 天的中文内容
results = collection.query(
    query_vector=query_embedding,
    n_results=10,
    where={
        "$and": [
            {"language": {"$eq": "zh"}},
            {"created_at": {"$gte": "2025-01-01"}}
        ]
    }
)
```

### 过滤策略

| 策略 | 流程 | 优点 | 缺点 |
|------|------|------|------|
| **预过滤** | 先过滤元数据，再在子集上搜索向量 | 结果精确满足条件 | 过滤后数据少，ANN 索引效率下降 |
| **后过滤** | 先搜索向量，再过滤元数据 | ANN 效率不受影响 | 可能返回不足 k 个结果 |
| **内联过滤** | 搜索过程中同时检查元数据 | 兼顾效率和准确性 | 实现复杂，各数据库策略不同 |

> 📝 不同数据库有不同的优化策略。Qdrant 采用"可调节预过滤"，Milvus 支持"基于分区的过滤"，Weaviate 则在搜索过程中内联过滤。

### 查询流程（以 HNSW 为例）

1. **客户端发送查询**：应用将自然语言/图片通过 embedding 模型转换为查询向量
2. **索引定位**：HNSW 从最高层的入口节点开始，贪心地跳到最近邻
3. **逐层下降**：每下降一层，搜索范围更精细
4. **底层搜索**：在最底层收集 top-k 个最近邻
5. **元数据过滤**：根据 where 条件过滤结果
6. **返回结果**：返回向量 ID + 距离分数 + 元数据

### 写入流程

1. **客户端插入数据**：向量 + 元数据 + 原始数据 ID
2. **写入 WAL**：确保持久化（WAL = Write-Ahead Log）
3. **更新索引**：将新向量插入 HNSW 图（找到最近邻、建立连接）
4. **更新元数据存储**：写入关联的标量字段
5. **确认写入**：返回成功

## 混合搜索

**混合搜索（Hybrid Search）** 将向量搜索（语义）与关键词搜索（精确匹配）结合，取两者之长。

```
查询: "Qdrant 性能优化"

纯向量搜索 → 可能返回: "Rust 实现的数据库性能分析"（语义相关但不含关键词）
纯关键词搜索 → 可能返回: "Qdrant 安装指南"（含关键词但不相关）
混合搜索 → 两者融合, 优先返回: "Qdrant 性能优化最佳实践"（语义相关 + 含关键词）
```

### RRF（Reciprocal Rank Fusion）融合算法

RRF 是最常用的混合搜索融合算法：

```
RRF_score(doc) = Σ 1 / (k + rank_i)

其中:
- k = 60 (常数, 防止排名靠前的项获得过大权重)
- rank_i = 该文档在第 i 个搜索通道中的排名
```

```python
def rrf_fusion(semantic_rankings: list, keyword_rankings: list, k: int = 60) -> dict:
    """Reciprocal Rank Fusion"""
    scores = {}

    for rank, doc_id in enumerate(semantic_rankings):
        scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank)

    for rank, doc_id in enumerate(keyword_rankings):
        scores[doc_id] = scores.get(doc_id, 0) + 1.0 / (k + rank)

    return dict(sorted(scores.items(), key=lambda x: x[1], reverse=True))

# 示例
semantic = ["doc3", "doc1", "doc5", "doc2", "doc4"]
keyword  = ["doc1", "doc2", "doc6", "doc3", "doc7"]

result = rrf_fusion(semantic, keyword)
# doc1 在语义搜索排第2, 关键词排第1 → RRF = 1/61 + 1/60 = 0.0331
# doc3 在语义搜索排第1, 关键词排第4 → RRF = 1/60 + 1/63 = 0.0325
# doc1 胜出 → 融合结果同时考虑了语义和关键词的排名
```


## 文档分块策略

在 RAG 等应用中，长文档需要切分为小块（chunk）后再 embedding。分块质量直接决定搜索质量。

### 分块方法对比

| 方法 | 描述 | 适用场景 |
|------|------|----------|
| **固定长度分块** | 按字符/token 数切割 | 快速实现，结构不明确的文本 |
| **重叠分块** | 固定长度 + 相邻块重叠 | 保留上下文，最常用 |
| **语义分块** | 按段落、标题、句子边界切割 | 结构化文档 |
| **递归分块** | 先按大结构切，再递归细分 | 长文档 |
| **基于 LLM 分块** | 用 LLM 判断语义边界 | 高质量需求，成本高 |

### 分块黄金规则

```
┌─────────────────────────────────────────────┐
│  块大小:  300-800 tokens（约 200-500 字）    │
│  重叠:    10-20% 的块大小                    │
│  粒度:    语义完整的段落 > 固定字数切割       │
│  元数据:  保留文档标题、章节、来源信息        │
└─────────────────────────────────────────────┘
```

### 分块代码示例

```python
def chunk_document(text: str, chunk_size: int = 500, overlap: int = 50) -> list[str]:
    """
    将文档分块，保留上下文重叠。

    Args:
        text: 原始文档文本
        chunk_size: 每块的字符数
        overlap: 相邻块的重叠字符数

    Returns:
        分块后的文本列表
    """
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size

        # 尝试在句号/换行处断开，避免切断句子
        if end < len(text):
            # 向后找最近的句号或换行
            for punct in ["\n", "。", ".", "！", "!", "？", "?"]:
                pos = text.rfind(punct, start + chunk_size // 2, end + 50)
                if pos != -1:
                    end = pos + 1
                    break

        chunks.append(text[start:end].strip())
        start = end - overlap

    return chunks

# 使用
long_article = "..."  # 你的长文档
chunks = chunk_document(long_article, chunk_size=500, overlap=50)
print(f"文档被切分为 {len(chunks)} 个块")
```

> ⚠️ **常见错误**：直接将 10000 字的长文丢进 embedding 模型生成单个向量。信息被稀释，搜索精度极差。一定要分块。


## 向量数据库 vs 传统数据库

| 维度 | 传统数据库（MySQL/PostgreSQL） | 向量数据库 |
|------|-------------------------------|-----------|
| **数据类型** | 结构化（行/列） | 高维向量 + 元数据 |
| **查询方式** | 精确匹配（`WHERE x = 1`） | 相似性搜索（top-k 最近邻） |
| **索引结构** | B-tree、Hash、GIN | HNSW、IVF、PQ |
| **擅长** | 事务、聚合、关联查询 | 语义搜索、推荐、RAG |
| **不擅长** | 高维相似性搜索 | 复杂 SQL 查询、事务 |

两者是**互补关系**，不是替代关系。如今边界正在模糊：PostgreSQL 通过 pgvector 扩展获得了向量搜索能力，但这更像是"也能做"而非"最擅长"。


## 关键要点

- **向量数据库的核心价值**是将非结构化数据的"语义相似度搜索"从不可能变为可能，且速度达到毫秒级
- **HNSW 是当前最通用的索引算法**，在速度和召回率之间取得了最佳平衡，但内存开销较大
- **选择 embedding 模型比选择向量数据库更重要**——垃圾向量进去，垃圾结果出来
- **相似度度量必须与 embedding 模型匹配**：归一化模型用内积，非归一化模型用余弦相似度
- **元数据过滤是生产必备能力**——纯粹的向量搜索在实际应用中几乎不存在
- **混合搜索（向量 + 关键词）是趋势**，可以同时捕获语义相似和精确匹配
- **Recall 和 QPS 之间存在权衡**，需要通过 benchmark 找到适合你场景的参数配置
- **文档分块质量直接决定搜索质量**——300-800 tokens + 10-20% 重叠是安全起点
- **分布式架构通过数据分片和副本实现水平扩展**，但也带来了一致性和运维复杂度


## 常见陷阱

### 陷阱 1：忽略 Embedding 模型的选择

> ❌ **错误**：随便选一个 embedding 模型就开始用

```python
# 用通用英文模型处理中文文本 → 搜索结果很差
from sentence_transformers import SentenceTransformer
model = SentenceTransformer('all-MiniLM-L6-v2')  # 英文为主
```

> ✅ **正确**：根据语言和领域选择合适的模型

```python
# 中文场景应该用中文优化的模型
from sentence_transformers import SentenceTransformer
model = SentenceTransformer('BAAI/bge-large-zh-v1.5')  # 中文优化
```

### 陷阱 2：相似度度量与模型不匹配

> ❌ **错误**：使用未归一化模型时配置了内积度量

```python
# 如果模型输出的向量没有归一化，内积的结果没有意义
collection.create_index("embedding", {"metric_type": "IP"})  # 可能导致结果错误
```

> ✅ **正确**：检查模型文档，确认正确的度量方式

```python
# 查看向量是否已归一化
import numpy as np
sample_vec = get_embedding("测试文本")
print(f"向量模: {np.linalg.norm(sample_vec):.4f}")  # 接近 1.0 = 已归一化
# 如果接近 1.0 → 用内积；否则用余弦相似度
```

### 陷阱 3：不做数据清洗就插入

> ❌ **错误**：直接将原始长文本整段丢进 embedding 模型

```python
# 一篇 10000 字的文章 → 单个向量 → 信息被稀释，搜索精度很差
embedding = get_embedding(entire_article)
```

> ✅ **正确**：对文档进行分块（chunking），每个块独立 embedding

### 陷阱 4：索引参数照搬默认值

> ❌ **错误**：不调优索引参数就上线

```python
# 默认参数可能不适合你的数据规模和性能要求
index_params = {"index_type": "HNSW", "params": {"M": 16, "efConstruction": 200}}
```

> ✅ **正确**：根据数据规模和性能要求做 benchmark

```python
# 关键参数指南：
# M: 16-64。数据量大（>1000万）时用较大值
# efConstruction: 100-500。越大构建越慢但索引质量越好
# ef_search: 50-200。查询时动态调整，越大召回率越高

# 建议：先用小数据集测试不同参数组合
for ef in [50, 100, 200]:
    results = collection.search(..., param={"ef": ef})
    recall = calculate_recall(results, ground_truth)
    print(f"ef={ef}, recall={recall:.4f}")
```

### 陷阱 5：不评估搜索质量就上线

> ❌ **错误**：凭"感觉"觉得结果还行就上线

> ✅ **正确**：用 Recall@K 量化评估

```python
def recall_at_k(approximate_results, ground_truth, k=10):
    """计算召回率"""
    approx_set = set(approximate_results[:k])
    true_set = set(ground_truth[:k])
    return len(approx_set & true_set) / k

# 建立评估数据集：
# 1. 选取 100-500 个查询
# 2. 用暴力搜索（Flat）得到精确结果作为 ground truth
# 3. 用你的 ANN 配置搜索，计算召回率
# 4. 目标：recall@10 >= 0.95
```


## 常见问题

### Q: 向量维度越高搜索越慢吗？

是的，但影响没有你想象的那么大。ANN 算法的瓶颈通常在图遍历的节点数，而不是单次距离计算。维度从 768 增加到 1536，搜索速度通常只下降 30-50%，而不是 2 倍。

更大的问题是**内存占用**——1536 维 × float32 = 6KB/向量。1000 万条数据就需要 60GB 内存。可以使用**量化**（将 float32 压缩为 int8 或更小）来缓解。

### Q: HNSW 和 IVF 应该怎么选？

| 场景 | 推荐 |
|------|------|
| 数据量 < 100 万，追求高召回率 | **HNSW** |
| 数据量 > 1000 万，内存受限 | **IVF-PQ** |
| 数据频繁增删 | **HNSW**（支持增量更新） |
| 批量写入为主，查询较少 | **IVF**（构建快） |
| 不确定 | **HNSW**（默认选择） |

### Q: RAG 中 chunk size 应该设多大？

取决于你的数据和查询特点：

- **300-500 tokens**：适合大多数场景
- **较小（100-200 tokens）**：适合精确问答（"这个函数的参数是什么？"）
- **较大（800-1000 tokens）**：适合需要上下文理解的场景（"总结这篇文章的论点"）

建议**先用 500 tokens 起步**，然后根据搜索质量调整。同时保留 10-20% 的重叠区域，避免重要信息被切断。

### Q: 如何评估向量搜索的质量？

使用**召回率（Recall@K）** 作为核心指标。具体方法：选取 100-500 个查询，用暴力搜索（Flat）得到精确结果作为 ground truth，然后用你的 ANN 配置搜索并计算召回率。目标：recall@10 >= 0.95。

## 总结

向量数据库的核心是**索引算法**和**距离度量**。HNSW 通过多层图结构实现了速度与精度的最佳平衡，IVF-PQ 则为大规模场景提供了内存友好的替代方案。相似度度量的选择必须与 embedding 模型的输出特性匹配——归一化用内积，否则用余弦相似度。

理解这些原理，你就能在任何向量存储工具上做出正确决策：选对索引类型、配对正确的度量方式、合理分块文档、量化评估搜索质量。这些知识比掌握某个特定工具的 API 更有价值，因为工具会变，原理不会。
